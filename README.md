# Micro IoT Cloud 🌩️

Примітивна міні-хмара на PHP для дзеркалення JSON-стану пристроїв (ESP32, інвертори тощо), читання їх через захищений API та відправки сповіщень у Telegram через Watchdog.

## Структура проєкту

- `cloud-code/` — код хмари та її корінь для розгортання: `index.html`, `.htaccess`, `install.php`, `adminpanel/`, `backend/`, `config/` і `storage/`.
- `examples/` — приклади панелей і прошивки, зокрема `jkbms/`, `test_esp32/` та `user_panel_sample/`.
- `cloud-code/config/rules.json.example` — шаблон конфігурації правил Telegram-сповіщень.
- `.github/` — налаштування репозиторію, зокрема повідомлення про підтримку проєкту.

Файли в `cloud-code/` описані нижче відносно кореня розгорнутої хмари.
Тека `НЕ_ЗАВАНТАЖУВАТИ_НА_СЕРВЕР/` не є частиною звичайного розгортання; у ній
зберігається аварійний скрипт відновлення адмінки.

## Швидкий старт

1. Дотримуйся інструкцій у розділі [Встановлення на Apache](#встановлення-на-apache): завантаж код, створи одноразовий ключ і запусти `install.php` через HTTPS.
2. Після встановлення видали `install.php`, налаштуй Telegram за потреби, створи пристрої в адмінці та перевір API.
3. Перевір HTTPS, API і Telegram вручну за інструкціями нижче, після чого налаштуй cron з абсолютними шляхами та журналом.

## Встановлення на Apache

Інсталятор створює нову SQLite-базу та першого адміністратора з обов'язковим 2FA. Він не перезаписує наявний конфіг, базу або `config/rules.json`. Потрібен Apache 2.4 з активними `mod_rewrite` і `AllowOverride` для `.htaccess`; для Nginx налаштуй еквівалентні правила окремо.

1. Скопіюй **вміст** `cloud-code/` у DocumentRoot домену, а не сам каталог. На сервері мають бути `index.html`, кореневий `.htaccess`, `install.php` і каталоги `adminpanel/`, `backend/`, `config/`, `storage/`. Теку `НЕ_ЗАВАНТАЖУВАТИ_НА_СЕРВЕР/` не завантажуй.
2. У `config/` завантаж `db.php` та `rules.json.example`, але **не завантажуй `config.php` чи `config.php.example`**: інсталятор створить серверний конфіг із вибраним шляхом до БД. Не завантажуй `sampleDB/`, README-файли, локальну SQLite-базу, активні `rules.json`/`states.json` чи JSON-файли пристроїв у `storage/`. У `storage/` залиш `storage/.htaccess`.
3. Переконайся, що кореневий `.htaccess` і `storage/.htaccess` не були пропущені FTP-клієнтом (приховані файли). Вони блокують прямий вебдоступ до конфігурації та сховища.
4. Створи одноразовий ключ із 64 випадкових hex-символів і запиши його в `config/install.key`. Наприклад, у терміналі сервера з DocumentRoot виконай `openssl rand -hex 32 > config/install.key`, потім `chmod 600 config/install.key`. Не використовуй приклад чи повторно використаний пароль.
5. Відкрий `https://твій-домен/install.php`, введи ключ, ім'я SQLite-файла, логін і надійний пароль адміністратора (не менше 12 символів). За замовчуванням база створюється як `config/cloud.sqlite`; можна вказати інше ім'я `.sqlite` у тій самій захищеній теці. Інсталятор створить `config.php`, таблиці, порожній `config/rules.json` (якщо його ще немає) і першого адміністратора.
6. Налаштуй 2FA за показаним QR-кодом або секретом, увійди в адмінку й **видали `install.php`**. Ключ видаляється автоматично після успіху; якщо видалення не вдалося, прибери `config/install.key` вручну.
7. Перевір із браузера або `curl`, що `config/config.php`, `config/cloud.sqlite`, `config/rules.json` і `storage/` не віддаються напряму (очікується `403`). Сам факт наявності `.htaccess` не гарантує, що Apache застосовує його: перевір `AllowOverride` на хостингу. Інсталятор перевіряє наявність потрібних файлів і прав запису, але не може надійно визначити конфігурацію вебсервера.

Не клади `install.key`, `recovery.key`, SQLite-базу чи runtime-файли `config.php`, `rules.json`, `states.json` до Git. `config.php.example` — лише шаблон для локальної розробки; на сервері інсталятор створює окремий конфіг.

## Аварійне відновлення доступу адміністратора

Якщо єдиний адміністратор втратив пароль або доступ до 2FA, процедура замінює
**обидва** значення для наявного адміністратора. SQLite-база та інші записи не
перезаписуються. Скрипт зберігається в
`cloud-code/НЕ_ЗАВАНТАЖУВАТИ_НА_СЕРВЕР/reset.php` і не повинен бути на сервері
під час звичайної роботи.

1. Через SSH у DocumentRoot створи одноразовий ключ:
   `openssl rand -hex 32 > config/recovery.key && chmod 600 config/recovery.key`.
   Не використовуй ключ інсталятора чи пароль замість нього.
2. Тимчасово завантаж **лише** `reset.php` у теку
   `НЕ_ЗАВАНТАЖУВАТИ_НА_СЕРВЕР/` у DocumentRoot. Відкрий
   `https://твій-домен/НЕ_ЗАВАНТАЖУВАТИ_НА_СЕРВЕР/reset.php`; не передавай ключ
   у URL і не відкривай сторінку через звичайний HTTP.
3. Введи логін адміністратора, новий пароль (від 12 символів) і ключ. Додай
   показаний QR-код до автентифікатора та введи актуальний шестизначний код.
   Зміни потраплять у БД лише після перевірки TOTP; після успіху ключ
   видаляється автоматично.
4. Негайно видали `reset.php` із сервера. Якщо процедура повідомила про помилку,
   перевір журнал PHP та переконайся, що ключ не видалений, перш ніж повторювати.

Використовуй процедуру лише на власному сервері й через HTTPS. Ключ дає змогу
замінити пароль і 2FA будь-якого адміністратора, тому створюй його безпосередньо
перед відновленням і не залишай скрипт чи ключ на сервері після завершення.

## Панель читання

Скопіюй `examples/user_panel_sample/` у каталог вебсервера з PHP та Apache. У серверному `read_config.json` задай HTTPS URL `backend/read.php` та API-токен користувача, згенерований в адмінці (поле конфігурації зберігає його під назвою `read_token`). Проксі передає токен у `api_token` сервер-сервером; браузер його не отримує. Інтерфейс дозволяє вибрати один із пристроїв, доступних цьому користувачу. Перевір, що `.htaccess` активний (`AllowOverride`) або налаштуй еквівалентне правило в конфігурації Apache.

Для панелі безпосередньо в Micro-IoT-Cloud відкрий `cloud-code/login/`.
Користувач входить своїм логіном, паролем і кодом 2FA та бачить лише призначені
йому адміністратором пристрої. Ця панель не потребує API-токена в браузері;
довідка доступна зі сторінки панелі. Файли інтерфейсу панелі й довідки
розміщені окремо від адмінки; точка входу — `/login/index.php`.

## Надсилання стану

API приймає тільки `POST` із JSON-об'єктом і перевіряє індивідуальний токен пристрою проти `devices.device_token` для відповідного `devices.id`. Токен можна передати в заголовку `Authorization: Bearer <device_token>` або в JSON-полі `device_token`. Ідентифікатор можна передати в JSON-полі `device_id`, query-параметрі `device` або заголовку `X-Device-Id` (саме в такому порядку пріоритету). Якщо токен передано одночасно в заголовку й JSON, вони мають збігатися.

Спільний токен запису більше не використовується. Перед надсиланням даних додай пристрій до SQLite і налаштуй згенерований для нього токен у прошивці.

Підтримуються два формати JSON:

1. Повний стан у тілі запиту — як і раніше; `device_id` задається query-параметром або заголовком, а індивідуальний токен — Bearer-заголовком.
2. Об'єкт-конверт з полями `device_id`, `device_token` і `payload`, де `payload` — JSON-об'єкт стану. Також `device_id` і `device_token` можна додати до повного об'єкта стану; поле `device_token` буде вилучене перед збереженням.

Після успішної автентифікації API повністю замінює JSON-файл пристрою в `storage/` і записує цей самий payload та серверний час у `devices.last_payload` і `devices.last_update`.

Приклад запиту з повним станом у тілі:

```sh
curl -i -X POST "https://yourdomain.com/backend/api.php?device=esp32_garage" \
     -H "Authorization: Bearer DEVICE_SPECIFIC_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"temperature": 22.5, "humidity": 60}'
```

Приклад конверта з токеном у тілі:

```json
{
  "device_id": "esp32_garage",
  "device_token": "DEVICE_SPECIFIC_TOKEN",
  "payload": {
    "temperature": 22.5,
    "humidity": 60
  }
}
```

`200` означає успішний запис; `400` — невалідний JSON або ID; `403` — неправильний/відсутній токен чи невідомий пристрій; `405` — використано не `POST`. Не додавай токен до URL.

## Читання стану

`GET https://yourdomain.com/backend/read.php?api_token=USER_API_TOKEN` повертає всі пристрої, прив'язані до користувача через `user_devices`, з їхніми назвами, дозволами, часом останнього оновлення з БД та станом із `storage/<device_id>.json`. `last_payload` у відповіді не використовується. Якщо користувацький токен невідомий або відсутній, сервер повертає `403`; неправильний метод — `405`.

API-токен потрібно згенерувати в адмінці для користувача та зберігати лише у серверному конфігу панелі. Токен передається в query string згідно з контрактом API, тому використовуй лише HTTPS і враховуй, що query string може потрапляти до access-логів вебсервера.

Приклад:

```sh
curl -i "https://yourdomain.com/backend/read.php?api_token=USER_API_TOKEN"
```

Відповідь — JSON-об'єкт, ключем кожного запису є `device_id`. У записі є `name`, `permission`, `last_update` із SQLite та `state`. Для пристрою без JSON-файлу `state` буде `null`. Час зміни файла на сервері окремо не повертається. Обидва приклади `read_proxy.php` передають час `last_update` у HTTP-заголовках для сумісності з інтерфейсом свіжості даних.

## Історія пристроїв

Адміністратор може ввімкнути один із режимів для кожного пристрою: погодинні
знімки за 7 днів або знімки кожні 30 хвилин за 3 дні. За замовчуванням історію
вимкнено. У кожному UTC-слоті записується перший пакет, який надійшов; пропущені
слоти залишаються порожніми. NDJSON-файл `storage/<device_id>.ndjson` містить
серверний час отримання, час початку слота, інтервал і стан пристрою.

Історію можна отримати окремо через
`GET https://yourdomain.com/backend/history.php?api_token=USER_API_TOKEN&device=DEVICE_ID`.
Endpoint перевіряє API-токен та доступ користувача до запитаного пристрою й
повертає NDJSON. Прострочені записи прибираються під час наступного запису або
читання; вимкнення історії в адмінці видаляє її файл. Прямий доступ до
`storage/` заблокований вебсервером. Токен передається в query string, тому
використовуй лише HTTPS і враховуй можливе потрапляння адреси до access-логів.

## Правила та сповіщення

`backend/watchdog.php` не запускається при кожному POST: це окремий CLI-скрипт, який періодично читає `config/rules.json` і файли з `storage/`. Запускай його через cron, не відкривай як вебсторінку. Правило має містити `device`, `param`, `operator`, `threshold`, `chat_id` і `message`. Підтримуються `<=`, `>=`, `==`, `!=`; вкладені поля задаються крапковим шляхом, наприклад `feeds.0.field1`. Числові значення порівнюються чисельно, а `==`/`!=` порівнюють типи точно: JSON `false` не дорівнює рядку `"false"`.

Поточна логіка надсилає сповіщення при першому спрацюванні, повторює його не частіше ніж раз на годину (`$cooldownTime`), а після нормалізації умови дозволяє нове негайне сповіщення. Якщо файл пристрою або потрібний параметр відсутній, правило пропускається; сигналу про відсутність пристрою/застарілі дані немає. Важливі обмеження: код не перевіряє відповідь Telegram API, але оновлює `config/states.json` так, ніби повідомлення надіслано; cURL-запит також не має timeout, а блокування від паралельних запусків cron не реалізовано. Для критичних аварій спершу доопрацюй підтвердження доставки, мережевий timeout і захист від накладання запусків.

Токен бота задається у змінній `$telegramBotToken` у файлі `backend/watchdog.php`, а `chat_id` — у кожному правилі. `curl` потрібен PHP і для Telegram, і для прикладу панелі в `examples/user_panel_sample/`. Переконайся, що сервер може встановлювати вихідні HTTPS-з'єднання до Telegram.

## Apache та доступ

`.htaccess` у `cloud-code/` (після копіювання — кореневий `.htaccess` сайту) передбачає Apache 2.4, увімкнені `mod_rewrite` і `mod_dir`, а також `AllowOverride` для `Options`, `FileInfo`, `AuthConfig` та `Indexes` (або `AllowOverride All`). Він вимикає лістинг каталогів, відкриває `index.html` як головну сторінку, передає `Authorization`, блокує прямий доступ до `storage/`, `sampleDB/`, `config/` (включно з правилами та станом watchdog) і веб-виклик `backend/watchdog.php`. Він **не** дозволяє звернення лише до `.php` і не реалізує rate limiting. Якщо використовуєш Nginx, правила `.htaccess` не діють: налаштуй еквівалентні обмеження в конфігурації Nginx.

Після встановлення перевір через HTTPS, що запити до `/storage/bms_data.json`, `/sampleDB/database.sqlite`, `/config/config.php`, `/config/rules.json`, `/config/states.json` і `/backend/watchdog.php` не віддають вміст (очікується `403`). `read_config.json` панелі захищений окремим `examples/user_panel_sample/.htaccess`; для нього також потрібен Apache з `AllowOverride` або відповідне правило вебсервера. Панель використовує серверний PHP-проксі, тому передавати токен браузеру чи налаштовувати CORS для цього прикладу не потрібно.

HTTPS обов'язковий для публічного сервера. `.htaccess` не замінює резервні копії, оновлення системи, сильні унікальні токени або обмеження запитів на рівні вебсервера/WAF.

## Перевірка перед запуском

1. Переконайся, що встановлені PHP CLI та веб-SAPI сумісної версії, `pdo_sqlite`, `json` і `curl`, а сертифікат HTTPS чинний. Запусти `php -v` і `php -m`.
2. Створи пристрій із його `id` та індивідуальним `device_token` у налаштованій SQLite-БД. Згенеруй API-токен читання для потрібного користувача в адмінці та задай його у серверному `read_config.json` панелі; для watchdog використовуй окремий токен Telegram-бота.
3. Перевір POST і GET прикладами вище. Спочатку використай тестовий ID, щоб не перезаписати стан реального пристрою. Успішний POST створює/замінює `storage/test_device.json`.
4. Перевір права користувача PHP CLI на читання `config/rules.json` та запис у `storage/` і `config/`, а також прямі HTTP-блокування за переліком вище.
5. Перед ручним запуском watchdog переглянь активні правила: він може негайно надіслати реальні тривоги. `php backend/watchdog.php` запускається з DocumentRoot хмари; HTTP-запит для нього має бути заборонений.
6. Для тесту Telegram тимчасово додай правило в `config/rules.json` й тестовий payload, що гарантовано його активують; після тесту віднови файл правил і видали тестовий файл. Успіх CLI без фактичного повідомлення не є підтвердженням доставки.
7. Після успішних ручних перевірок додай cron від імені користувача з потрібними правами. Заміни шлях і перевіряй журнал:

```cron
* * * * * /usr/bin/php /абсолютний/шлях/до/проєкту/backend/watchdog.php >> /абсолютний/шлях/до/watchdog.log 2>&1
```

`api.php` записує файл напряму через `file_put_contents`, без тимчасового файла та атомарного `rename`. При одночасному читанні й записі теоретично можливий неповний JSON; для вимог без втрати узгодженого знімка запис треба доопрацювати. Також регулярно резервуй `storage/`, `config/rules.json` і `config/states.json`.
