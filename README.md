# Micro IoT Cloud 🌩️

Примітивна міні-хмара на PHP для дзеркалення JSON-стану пристроїв (ESP32, інвертори тощо), читання їх через захищений API та відправки сповіщень у Telegram через Watchdog.

## Структура проєкту

- `backend/api.php` — приймає POST-запити від девайсів (з токеном), валідує JSON і пише у кореневу `storage/`.
- `backend/read.php` — віддає актуальний JSON за запитом (з токеном).
- `backend/watchdog.php` — фоновий скрипт, який перевіряє кореневий `rules.json` і шле алярми в Telegram.
- `user_panel_sample/` — приклад веб-панелі для читання пристроїв через віддалений `backend/read.php`.
- `.htaccess` — Apache-правила для захисту `storage/`, конфігурації та CLI-only watchdog.

## Швидкий старт

1. Розмісти проєкт так, щоб його корінь був DocumentRoot домену: `backend/`, `storage/`, `rules.json` і `.htaccess` мають бути на очікуваних місцях.
2. Заміни заглушки токенів у `backend/api.php`, `backend/read.php` і `backend/watchdog.php`. Код наразі читає секрети з PHP-файлів, а не із зовнішнього конфіга; не додавай справжні ключі до публічного Git-репозиторію.
3. Перевір права запису для `storage/` і `states.json` від імені користувача, під яким працюватиме PHP CLI.
4. Перевір HTTPS, API і Telegram вручну за інструкціями нижче, після чого налаштуй cron з абсолютними шляхами та журналом.

## Панель читання

Скопіюй `user_panel_sample/` у каталог вебсервера з PHP та Apache. У `read_config.json` задай HTTPS URL свого `backend/read.php` і токен читання, який налаштований у хмарі. Відкрий `user_panel_sample/index.html`, введи ID пристрою та натисни «Зчитати дані». PHP-проксі передає токен сервер-сервером; браузер його не отримує. Перевір, що `.htaccess` активний (`AllowOverride`) або налаштуй еквівалентне правило в конфігурації Apache.

## Надсилання стану

API приймає тільки `POST` із заголовком `Authorization: Bearer ...` і JSON-об'єктом. `device` — це лише ім'я файлу, не засіб авторизації. Його можна задати в query string або заголовком `X-Device-Id`; якщо задано обидва, перевага за query string. Кожен запит повністю замінює попередній знімок цього пристрою, а не зливає окремі поля.

Приклад запиту:

```sh
curl -i -X POST "https://yourdomain.com/backend/api.php?device=esp32_garage" \
     -H "Authorization: Bearer ЗАМІНИТИ_НА_ТОКЕН_З_api.php" \
     -H "Content-Type: application/json" \
     -d '{"temperature": 22.5, "humidity": 60}'
```

`200` означає успішний запис; `400` — JSON невалідний або не є об'єктом; `401` — відсутній чи неправильний токен; `405` — використано не `POST`. Токен передавай тільки заголовком, не додавай його до URL.

## Читання стану

Запит читання — `GET https://yourdomain.com/backend/read.php?device=esp32_garage` із заголовком `Authorization: Bearer READ_TOKEN`. Для читання використовується окремий токен із `backend/read.php`; токен запису та токен читання не взаємозамінні. Відповіді: `200` — JSON стану, `401` — неправильний токен, `404` — файл пристрою відсутній.

```sh
curl -i "https://yourdomain.com/backend/read.php?device=esp32_garage" \
     -H "Authorization: Bearer ЗАМІНИТИ_НА_READ_TOKEN"
```

## Правила та сповіщення

`backend/watchdog.php` не запускається при кожному POST: це окремий CLI-скрипт, який періодично читає `rules.json` і файли з `storage/`. Запускай його через cron, не відкривай як вебсторінку. Правило має містити `device`, `param`, `operator`, `threshold`, `chat_id` і `message`. Підтримуються `<=`, `>=`, `==`, `!=`; вкладені поля задаються крапковим шляхом, наприклад `feeds.0.field1`. Числові значення порівнюються чисельно, а `==`/`!=` порівнюють типи точно: JSON `false` не дорівнює рядку `"false"`.

Поточна логіка надсилає сповіщення при першому спрацюванні, повторює його не частіше ніж раз на годину (`$cooldownTime`), а після нормалізації умови дозволяє нове негайне сповіщення. Якщо файл пристрою або потрібний параметр відсутній, правило пропускається; сигналу про відсутність пристрою/застарілі дані немає. Важливі обмеження: код не перевіряє відповідь Telegram API, але оновлює `states.json` так, ніби повідомлення надіслано; cURL-запит також не має timeout, а блокування від паралельних запусків cron не реалізовано. Для критичних аварій спершу доопрацюй підтвердження доставки, мережевий timeout і захист від накладання запусків.

Токен бота задається в `backend/watchdog.php`, а `chat_id` — у кожному правилі. `curl` потрібен PHP і для Telegram, і для прикладу панелі в `user_panel_sample/`. Переконайся, що сервер може встановлювати вихідні HTTPS-з'єднання до Telegram.

## Apache та доступ

Кореневий `.htaccess` передбачає Apache 2.4, увімкнені `mod_rewrite` і `mod_dir`, а також `AllowOverride` для `Options`, `FileInfo`, `AuthConfig` та `Indexes` (або `AllowOverride All`). Він вимикає лістинг каталогів, відкриває `index.htm` як головну сторінку, передає `Authorization`, блокує прямий доступ до `storage/`, `rules.json`, `states.json` і веб-виклик `backend/watchdog.php`. Він **не** дозволяє звернення лише до `.php` і не реалізує rate limiting. Якщо використовуєш Nginx, правила `.htaccess` не діють: налаштуй еквівалентні обмеження в конфігурації Nginx.

Після встановлення перевір через HTTPS, що запити до `/storage/bms_data.json`, `/rules.json`, `/states.json` і `/backend/watchdog.php` не віддають вміст (очікується `403`). `read_config.json` панелі захищений окремим `user_panel_sample/.htaccess`; для нього також потрібен Apache з `AllowOverride` або відповідне правило вебсервера. Панель використовує серверний PHP-проксі, тому передавати токен браузеру чи налаштовувати CORS для цього прикладу не потрібно.

HTTPS обов'язковий для публічного сервера. `.htaccess` не замінює резервні копії, оновлення системи, сильні унікальні токени або обмеження запитів на рівні вебсервера/WAF.

## Перевірка перед запуском

1. Переконайся, що встановлені PHP CLI та веб-SAPI сумісної версії, розширення `json` і `curl`, а сертифікат HTTPS чинний. Запусти `php -v` і `php -m`.
2. Замінити заглушки токенів у `backend/api.php`, `backend/read.php` і `backend/watchdog.php`; використовуй різні довгі випадкові секрети. Переконайся, що `read_config.json` на панелі містить HTTPS URL і саме read-токен.
3. Перевір POST і GET прикладами вище. Спочатку використай тестовий ID, щоб не перезаписати стан реального пристрою. Успішний POST створює/замінює `storage/test_device.json`.
4. Перевір права користувача PHP CLI на запис у `storage/` і `states.json`, а також прямі HTTP-блокування за переліком вище.
5. Перед ручним запуском watchdog переглянь активні правила: він може негайно надіслати реальні тривоги. `php backend/watchdog.php` запускається з кореня проєкту; HTTP-запит для нього має бути заборонений.
6. Для тесту Telegram тимчасово додай правило й тестовий payload, що гарантовано його активують; після тесту віднови `rules.json` і видали тестовий файл. Успіх CLI без фактичного повідомлення не є підтвердженням доставки.
7. Після успішних ручних перевірок додай cron від імені користувача з потрібними правами. Заміни шлях і перевіряй журнал:

```cron
* * * * * /usr/bin/php /абсолютний/шлях/до/проєкту/backend/watchdog.php >> /абсолютний/шлях/до/watchdog.log 2>&1
```

`api.php` записує файл напряму через `file_put_contents`, без тимчасового файла та атомарного `rename`. При одночасному читанні й записі теоретично можливий неповний JSON; для вимог без втрати узгодженого знімка запис треба доопрацювати. Також регулярно резервуй `storage/`, `rules.json` і `states.json`.

## Читання стану пристроїв і контроль актуальності даних

Проєкт підтримує окремий API для читання даних пристрою з `storage/` без передачі секретного токена у браузер. Це дозволяє:
- безпечно читати JSON-файли з серверної сторони;
- отримувати інформацію про час останньої модифікації файлу;
- відображати на веб-сторінці, коли дані були актуально оновлені;
- розрізняти локальний час браузера та UTC для зручного контролю синхронізації.

---

## 1. Як читати JSON через API

Запит:

```bash
curl -sD - "https://yourdomain.com/backend/read.php?device=esp32_garage" \
  -H "Authorization: Bearer READ_TOKEN"
```

Параметри:
- `device` — ім’я пристрою, який відповідає файлу у каталозі `storage/`
- `Authorization: Bearer READ_TOKEN` — токен доступу для читання

Приклад:
- якщо у `storage/` є файл `esp32_garage.json`, то `read.php` відкриє його і поверне JSON;
- якщо файлу немає — сервер поверне `404`;
- якщо токен неправильний — `401 Unauthorized`.

### Відповідь API

API повертає не лише JSON, а й HTTP-заголовки з часом актуальності файлу:

- `Last-Modified` — стандартний HTTP-час останньої модифікації в GMT;
- `X-File-Modified-At` — ISO-8601 час у форматі `2026-10-24T12:34:56+00:00`;
- `X-File-Modified-Unix` — UNIX timestamp у секундах.

Приклад заголовків відповіді:

```http
HTTP/1.1 200 OK
Date: Fri, 24 Oct 2026 12:34:56 GMT
Last-Modified: Fri, 24 Oct 2026 12:34:56 GMT
X-File-Modified-At: 2026-10-24T12:34:56+00:00
X-File-Modified-Unix: 1761297296
Content-Type: application/json
```

Тіло відповіді — це JSON, що зберігається у файлі:

```json
{
  "device": "esp32_garage",
  "battery_voltage": 52.14,
  "battery_power": 2400.5,
  "connected": true
}
```

## 2. Як працює передача часу актуальності

Система використовує три рівні:

### 2.1. Сервер записує JSON у storage

Коли пристрій або бекенд пише нові дані, вони зберігаються в файлі типу:

```text
storage/esp32_garage.json
```

Операційна система зберігає у файлі час останньої модифікації (`filemtime`).

### 2.2. backend/read.php додає заголовки часу

У `backend/read.php` виконується наступне:

```php
$lastModifiedUnix = filemtime($filePath);
header('Last-Modified: ' . gmdate('D, d M Y H:i:s', $lastModifiedUnix) . ' GMT');
header('X-File-Modified-At: ' . gmdate('c', $lastModifiedUnix));
header('X-File-Modified-Unix: ' . $lastModifiedUnix);
header('Content-Type: application/json');
readfile($filePath);
```

Це означає:
- система читає реальний час оновлення файлу;
- додає його у заголовки HTTP;
- не змінює JSON-вміст;
- дозволяє клієнту отримати timestamp окремо без парсингу даних.

### 2.3. read_proxy.php пересилає заголовки далі до frontend

У веб-панелі (`jkbms/read_proxy.php`) є server-side проксі, який робить запит до `backend/read.php` через cURL і передає назад потрібні заголовки.

Основна логіка така:

```php
foreach (['Last-Modified', 'X-File-Modified-At', 'X-File-Modified-Unix'] as $headerName) {
    if (isset($upstreamHeaders[strtolower($headerName)])) {
        header($headerName . ': ' . $upstreamHeaders[strtolower($headerName)], false);
    }
}
```

Тобто:
- браузер не взаємодіє напряму з cloud read API;
- серверний проксі передає заголовки назад користувачу;
- токен залишається на сервері, а не передається в браузер.

## 3. Чому це потрібно

Це критично для розуміння того, коли дані були оновлені.

Наприклад:
- пристрій може оновлювати дані раз на 5 секунд;
- іноді клієнт бачить старі або неактуальні дані;
- окремо від JSON треба знати: “коли саме цей файл був записаний?”;
- без цього неможливо адекватно судити, чи дані свіжі, чи вже застаріли.

Саме тому в інтерфейсі є рядок:

```text
дані отримано за: 24.10.2026, 12:34:56 (UTC: 2026-10-24 12:34:56 UTC)
```

Це дає зрозуміти:
- коли саме файл storage був оновлений;
- чи не зберігаються застарілі значення;
- чи нові дані реально прийшли з пристрою.

## 4. Як це відображається у веб-інтерфейсі

У `jkbms/index.htm` виконується наступне:

```js
const modifiedAt = response.headers.get('X-File-Modified-At')
  || response.headers.get('Last-Modified')
  || response.headers.get('X-File-Modified-Unix');

updateDataFreshness(modifiedAt || '—');
```

Після цього відбувається форматування часу. Важливо:
- локальний час браузера береться як основний;
- у дужках додається UTC;
- це зручно, якщо користувач відкриває панель з іншої часової зони.

Формат виводу:

```text
дані отримано за: 24.10.2026, 15:34:56 (UTC: 2026-10-24 12:34:56 UTC)
```

Тобто:
- `24.10.2026, 15:34:56` — локальний час користувача;
- `UTC: 2026-10-24 12:34:56 UTC` — універсальний час, який легко зіставити з серверами або іншими системами.

## 5. Контроль актуальності в практиці

Ця механіка корисна для:
- моніторингу стану батареї;
- перевірки, чи пристрій ще живий;
- визначення, чи зв’язок працює стабільно;
- виявлення пропусків або “зависання” JSON;
- оцінки, чи нові дані щойно записані в `storage/`.

Наприклад:
- якщо було відновлення мережі або перезавантаження пристрою;
- якщо файл оновлюється рідше, ніж очікувалося;
- якщо пристрій працює, але не записує нові дані;
- якщо користувач відкрив сторінку пізніше і хоче перевірити реальну свіжість інформації.

Тоді достатньо подивитись на рядок:

```text
дані отримано за:
```

і відразу зрозуміти, коли останній раз змінювався JSON.

Потік виглядає так:

`браузер -> read_proxy.php -> backend/read.php -> storage/<device>.json -> filemtime -> HTTP headers -> браузер -> відображення “дані отримано за ...”`

## 7. Безпека та роль токена

Читання даних відбувається через окремий токен:
- один токен для запису/оновлення;
- окремий токен для читання.

Це потрібно для:
- уникнення передачі секретного ключа у клієнтський JS;
- роботи через серверний проксі;
- скорочення ризику викрадення токена через браузер.

Тобто:
- `backend/read.php` перевіряє `Authorization: Bearer READ_TOKEN`;
- `read_proxy.php` передає токен сервер-сервером;
- користувач у браузері не бачить і не працює з токеном напряму.

## 9. Підсумок

Функція актуальності даних працює таким чином:
- JSON зберігається у `storage/`;
- сервер визначає час останньої модифікації файлу через `filemtime()`;
- додає цей час у HTTP-заголовки;
- проксі переносить заголовки в frontend;
- веб-інтерфейс відображає “дані отримано за: …”;
- це дозволяє на боці користувача швидко оцінити свіжість даних без розбору JSON.

Це особливо важливо для систем моніторингу, де дані можуть змінюватись регулярно, а метрика “час останньої оновленої записи” є не менш важливою, ніж самі показники.
