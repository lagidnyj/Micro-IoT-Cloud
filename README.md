# Micro IoT Cloud 🌩️

Примітивна міні-хмара на PHP для дзеркалення JSON-стану пристроїв (ESP32, інвертори тощо), читання їх через захищений API та відправки сповіщень у Telegram через Watchdog.

## Структура проєкту

- `api.php` — приймає POST-запити від девайсів (з токеном), валідує JSON і пише у `storage/`.
- `read.php` — віддає актуальний JSON за запитом (з токеном).
- `watchdog.php` — фоновий скрипт, який перевіряє правила (`rules.json`) і шле алярми в Telegram.
- `.htaccess` — захищає папку `storage/` від прямих переглядів з інтернету.

## Швидкий старт

1. Створи папку `storage/` поруч зі скриптами.
2. Пропиши свої токени в `api.php`, `read.php` та `watchdog.php` (або винеси у конфіг).
3. Налаштуй виконання `watchdog.php` через `cron` кожну хвилину:
   `* * * * * /usr/bin/php /шлях/до/проєкту/watchdog.php >/dev/null 2>&1`

## Як це використовувати з девайсів (стара умова для роботи без авторизації) можливо не працюватиме
Через URL-параметр (найпростіше для ESP32/Arduino чи легких скриптів):
POST [https://yourdomain.com/api.php?device=esp32_garage](https://yourdomain.com/api.php?device=esp32_garage)

Через кастомний заголовок (зручніше, якщо URL завжди однаковий):
POST [https://yourdomain.com/api.php](https://yourdomain.com/api.php) з заголовком X-Device-Id: inverter_master

Важливі нюанси архітектури:
Атомарність запису: Якщо пристрій читає файл у момент, коли PHP його перезаписує, може виникнути "битий" JSON. Для критичних систем краще записувати у тимчасовий файл, а потім робити rename(), але для простого дзеркалення поточного стану зазвичай вистачає і прямого file_put_contents.

## Як відправляти запити з токеном:
Зі скрипта або ESP32 (cURL приклад):

curl -X POST "https://yourdomain.com/api.php?device=esp32_garage" \
     -H "Authorization: Bearer ТВОЙ_СЕКРЕТНИЙ_КЛЮЧ_ЯКИЙ_ТРЕБА_ЗМІНИТИ" \
     -H "Content-Type: application/json" \
     -d '{"temperature": 22.5, "humidity": 60}'

## Додатковий захист від ботів на рівні сервера (.htaccess)
Якщо боти бомблять сам PHP-скрипт тисячами запитів на секунду (ігноруючи токен, але навантажуючи вебсервер), найкраще відсікати їх на рівні Nginx або .htaccess (якщо стоїть Apache):
Дозволь POST-запити тільки для цього файлу.
Обмеж кількість запитів (Rate Limiting), якщо твої пристрої шлють дані не надто часто (наприклад, не частіше ніж раз на кілька секунд).

## читання з інших серверів/клієнтів:
Через HTTP (найпростіший і найбезпечніший):  read.php дає можливість віддавати JSON за токеном (GET /read.php?device=esp32). Тоді будь-який зовнішній сервер чи мобільний застосунок зможе отримати актуальний стан одним запитом.

Аналітичні плюси та мінуси рішення:
Плюси:
Нульова залежність від структури: Новий пристрій присилає абсолютно новий формат ключів — сервер просто пише його в свій .json файл, не ламаючи жодних схем таблиць в SQL.
Простота міграції/бекпу: Скопіювати папку storage/ на інший сервер — це справа однієї команди.
Прозорість: У будь-який момент можна відкрити файл утилітою типу cat чи в редакторі й побачити сирі дані.

На що звернути увагу на майбутнє:
Швидкодія файлової системи: Якщо пристроїв стане сотні чи тисячі, ОС почне витрачати час на пошук файлів у директорії. Але для десятків девайсів це працюватиме роками без навантаження на CPU.

Атомарний запис (коли захочеш усунути биті файли): Зараз file_put_contents пише файл напряму. Якщо зчитати його в мілісекунду запису, можна зловити шматок старого й шматок нового JSON. Коли набридне ловити битий JSON, робиться це в 2 рядки через запис у тимчасовий файл і функцію rename() (вона атомарна для ОС).

## Виділення окремого субдомена (наприклад, api.yourdomain.com або cloud.yourdomain.com)
це ідеальне ізолювання. Ти зможеш повністю контролювати правила доступу, CORS (якщо фронтенд на іншій адресі) і налаштувати під це окремий легкий віртуальний хост чи конфіг у Nginx/Apache.
Оскільки ти плануєш підіймати там і вебморди, ось три маленькі поради на майбутнє, які зекономлять час, коли проєкт почне розростатись:
Структура папок: Тримай бекенд (api.php, read.php) у захищеній папці (або на рівень вище/в окремій піддиректорії), а фронтенд-морди — в іншій. Щоб код пристроїв не перетинався з HTML/JS-файлами інтерфейсу.
CORS-заголовки у read.php: Якщо твоя майбутня вебморда житиме на іншому домені або локально під час розробки (наприклад, localhost:3000), не забудь додати у read.php відповідні заголовки Access-Control-Allow-Origin, інакше браузер заблокує запити.
Атомарний запис: Коли почнеш реалізовувати api.php на практиці, згадай про те, щоб записувати файл через тимчасовий (tempnam + rename), якщо браузер чи дашборд почне іноді ловити обрізаний JSON у момент оновлення.

## Ось готовий та протестований варіант .htaccess під Apache, який вирішує всі ключові завдання безпеки для твоєї приватної хмари:
Повністю закриває прямий веб-доступ до папки storage/ (помилка 403 Forbidden при спробі відкрити файл напряму).
Забороняє будь-яке сканування лістингу папок.
Дозволяє звернення лише до розширення .php (api.php, read.php тощо).
Налаштовує відправку токенів авторизації через заголовки (в Apache це поширений «підводний камінь», коли сервер за замовчуванням ріже заголовок Authorization).
.htaccess (покласти в корінь субдомена)

## Альтернатива (якщо є можливість створити окремий .htaccess всередині storage/):
Якщо зручніше, ти можеш додатково покласти ще один маленький файл .htaccess прямо всередину папки storage/:
Цей єдиний рядок надійно гарантує, що жоден веб-клієнт не зможе прочитати файли storage/*.json напряму з браузера, оминаючи твій read.php. Сам PHP-скрипт при цьому матиме повний доступ на читання та запис, оскільки він працює на рівні файлової системи сервера, а не через HTTP-запити.

## Рекомендована структура на субдомені:

subdomain_root/
├── .htaccess
├── api.php       (приймає POST з токеном -> пише в storage)
├── read.php      (приймає GET з токеном -> віддає з storage)
├── index.html    (або твої майбутні веб-морди)
└── storage/      (захищена папка)
    ├── .htaccess (опціонально: Require all denied)
    ├── esp32_garage.json
    └── inverter.json

## Варіант PUSH через Telegram-бот (Найкращий та найшвидший)
Оскільки Telegram встановлений майже у всіх, це ідеальне рішення. Бот пробиває фоновий режим Android, а сповіщення приходять миттєво.
Як це працює в твоєму api.php:
Коли пристрій надсилає JSON, PHP-скрипт декодує його, перевіряє тригери (наприклад, soc <= 5 або grid_status == "offline") і робить один curl-запит до Telegram API.

Порада щодо захисту від «спаму алармами»:
Щоб інвертор, при надсиланні JSON щосекунди, не заспамив Telegram 1000 повідомленнями про SOC 5%, у файл стану (або окремий прапорець) варто зберігати час останнього сповіщення (last_alert_time) або поточний статус тривоги, щоб надсилати пуш тільки при зміні стану (state shift).

## Як це запускати?
Через Cron (найпростіше і найзручніше):
Налаштовуєш у системі виконання watchdog.php раз на хвилину:
* * * * * /usr/bin/php /path/to/subdomain/watchdog.php >/dev/null 2>&1
Watchdog пробігає по всіх файлах, звіряє правила і засинає. Ніяких зайвих навантажень на API.

Або "на льоту" з api.php:
Можна викликати його в неблокуючому фоні одразу після запису файлу, але для перевірки умов по часу чи стабільності cron зазвичай надійніший.

## Як реалізувати кулдаун (або збереження стану попередньої тривоги) у watchdog.php, щоб сповіщення надсилалося лише один раз при зміні стану, а не щоразу при запуску скрипта?

Для реалізації захисту від спаму (щоб алярм летів тільки при зміні стану або згідно з кулдауном), є два основних підходи:
State-based (за зміною стану): Запам'ятовувати, чи була тривога активана минулого разу. Повторний пуш летить лише тоді, коли ситуація нормалізувалася, а потім знову перетнула трешхолд.
Cooldown (за таймером): Дозволяти надсилати сповіщення не частіше, ніж раз на N хвилин (наприклад, раз на годину), навіть якщо умова виконується постійно.
Найкраще працює комбінований варіант: сповіщення відправляється миттєво при досягненні трешхолду, а повторні блокуються на певний час (кулдаун) або доки стан не зміниться.
Реалізація у watchdog.php через файл станів (states.json)
Створимо невеликий механізм збереження стану для кожного правила (або унікального ідентифікатора правила). Ми можемо зберігати час останнього сповіщення (last_sent) і попередній статус тривоги (was_triggered).
