# Micro IoT Cloud 🌩️

Примітивна міні-хмара на PHP для дзеркалення JSON-стану пристроїв (ESP32, інвертори тощо), читання їх через захищений API та відправки сповіщень у Telegram через Watchdog.

## Структура проєкту

- `backend/api.php` — приймає POST-запити від девайсів (з токеном), валідує JSON і пише у кореневу `storage/`.
- `backend/read.php` — віддає актуальний JSON за запитом (з токеном).
- `backend/watchdog.php` — фоновий скрипт, який перевіряє кореневий `rules.json` і шле алярми в Telegram.
- `user_panel_sample/` — приклад веб-панелі для читання пристроїв через віддалений `backend/read.php`.
- `.htaccess` — Apache-правила для захисту `storage/`, конфігурації та CLI-only watchdog.

## Швидкий старт

1. Розмісти проєкт так, щоб його корінь був DocumentRoot домену: `backend/`, `storage/`, `rules.json` і `.htaccess` мають бути на очікуваних місцях.
2. Створи пристрої та індивідуальні токени запису в адмінці. Там само згенеруй API-токен читання для користувача й задай його у серверній конфігурації потрібної панелі. Токен Telegram-бота налаштовується у `backend/watchdog.php`. Не додавай справжні секрети до публічного Git-репозиторію.
3. Перевір права запису для `storage/` і `states.json` від імені користувача, під яким працюватиме PHP CLI.
4. Перевір HTTPS, API і Telegram вручну за інструкціями нижче, після чого налаштуй cron з абсолютними шляхами та журналом.

## Панель читання

Скопіюй `user_panel_sample/` у каталог вебсервера з PHP та Apache. У серверному `read_config.json` задай HTTPS URL `backend/read.php` та API-токен користувача, згенерований в адмінці (поле конфігурації зберігає його під назвою `read_token`). Проксі передає токен у `api_token` сервер-сервером; браузер його не отримує. Інтерфейс дозволяє вибрати один із пристроїв, доступних цьому користувачу. Перевір, що `.htaccess` активний (`AllowOverride`) або налаштуй еквівалентне правило в конфігурації Apache.

## Надсилання стану

API приймає тільки `POST` із JSON-об'єктом і перевіряє індивідуальний токен пристрою проти `devices.device_token` для відповідного `devices.id`. Токен можна передати в заголовку `Authorization: Bearer <device_token>` або в JSON-полі `device_token`. Ідентифікатор можна передати в JSON-полі `device_id`, query-параметрі `device` або заголовку `X-Device-Id` (саме в такому порядку пріоритету). Якщо токен передано одночасно в заголовку й JSON, вони мають збігатися.

Спільний токен запису більше не використовується. Перед надсиланням даних додай пристрій до SQLite і налаштуй згенерований для нього токен у прошивці.

Підтримуються два формати JSON:

1. Повний стан у тілі запиту — як і раніше; `device_id` задається query-параметром або заголовком, а індивідуальний токен — Bearer-заголовком.
2. Об'єкт-конверт з полями `device_id`, `device_token` і `payload`, де `payload` — JSON-об'єкт стану. Також `device_id` і `device_token` можна додати до повного об'єкта стану; поле `device_token` буде вилучене перед збереженням.

Після успішної автентифікації API повністю замінює JSON-файл пристрою в `storage/` і записує цей самий payload та серверний час у `devices.last_payload` і `devices.last_update`.

Приклад запиту з повним станом у тілі:

```sh
curl -i -X POST "https://yourdomain.com/backend/api.php?device=esp32_garage" \
     -H "Authorization: Bearer DEVICE_SPECIFIC_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"temperature": 22.5, "humidity": 60}'
```

Приклад конверта з токеном у тілі:

```json
{
  "device_id": "esp32_garage",
  "device_token": "DEVICE_SPECIFIC_TOKEN",
  "payload": {
    "temperature": 22.5,
    "humidity": 60
  }
}
```

`200` означає успішний запис; `400` — невалідний JSON або ID; `403` — неправильний/відсутній токен чи невідомий пристрій; `405` — використано не `POST`. Не додавай токен до URL.

## Читання стану

`GET https://yourdomain.com/backend/read.php?api_token=USER_API_TOKEN` повертає всі пристрої, прив'язані до користувача через `user_devices`, з їхніми назвами, дозволами, часом останнього оновлення з БД та станом із `storage/<device_id>.json`. `last_payload` у відповіді не використовується. Якщо користувацький токен невідомий або відсутній, сервер повертає `403`; неправильний метод — `405`.

API-токен потрібно згенерувати в адмінці для користувача та зберігати лише у серверному конфігу панелі. Токен передається в query string згідно з контрактом API, тому використовуй лише HTTPS і враховуй, що query string може потрапляти до access-логів вебсервера.

Приклад:

```sh
curl -i "https://yourdomain.com/backend/read.php?api_token=USER_API_TOKEN"
```

Відповідь — JSON-об'єкт, ключем кожного запису є `device_id`. У записі є `name`, `permission`, `last_update`, `file_modified_unix` і `state`. Для пристрою без JSON-файлу `state` буде `null`. Заголовки `Last-Modified`, `X-File-Modified-At` та `X-File-Modified-Unix` збережені для сумісності й відображають найновіший файл серед доступних користувачу пристроїв.

## Правила та сповіщення

`backend/watchdog.php` не запускається при кожному POST: це окремий CLI-скрипт, який періодично читає `rules.json` і файли з `storage/`. Запускай його через cron, не відкривай як вебсторінку. Правило має містити `device`, `param`, `operator`, `threshold`, `chat_id` і `message`. Підтримуються `<=`, `>=`, `==`, `!=`; вкладені поля задаються крапковим шляхом, наприклад `feeds.0.field1`. Числові значення порівнюються чисельно, а `==`/`!=` порівнюють типи точно: JSON `false` не дорівнює рядку `"false"`.

Поточна логіка надсилає сповіщення при першому спрацюванні, повторює його не частіше ніж раз на годину (`$cooldownTime`), а після нормалізації умови дозволяє нове негайне сповіщення. Якщо файл пристрою або потрібний параметр відсутній, правило пропускається; сигналу про відсутність пристрою/застарілі дані немає. Важливі обмеження: код не перевіряє відповідь Telegram API, але оновлює `states.json` так, ніби повідомлення надіслано; cURL-запит також не має timeout, а блокування від паралельних запусків cron не реалізовано. Для критичних аварій спершу доопрацюй підтвердження доставки, мережевий timeout і захист від накладання запусків.

Токен бота задається в `backend/watchdog.php`, а `chat_id` — у кожному правилі. `curl` потрібен PHP і для Telegram, і для прикладу панелі в `user_panel_sample/`. Переконайся, що сервер може встановлювати вихідні HTTPS-з'єднання до Telegram.

## Apache та доступ

Кореневий `.htaccess` передбачає Apache 2.4, увімкнені `mod_rewrite` і `mod_dir`, а також `AllowOverride` для `Options`, `FileInfo`, `AuthConfig` та `Indexes` (або `AllowOverride All`). Він вимикає лістинг каталогів, відкриває `index.htm` як головну сторінку, передає `Authorization`, блокує прямий доступ до `storage/`, `sampleDB/`, `config/`, `rules.json`, `states.json` і веб-виклик `backend/watchdog.php`. Він **не** дозволяє звернення лише до `.php` і не реалізує rate limiting. Якщо використовуєш Nginx, правила `.htaccess` не діють: налаштуй еквівалентні обмеження в конфігурації Nginx.

Після встановлення перевір через HTTPS, що запити до `/storage/bms_data.json`, `/sampleDB/database.sqlite`, `/config/config.php`, `/rules.json`, `/states.json` і `/backend/watchdog.php` не віддають вміст (очікується `403`). `read_config.json` панелі захищений окремим `user_panel_sample/.htaccess`; для нього також потрібен Apache з `AllowOverride` або відповідне правило вебсервера. Панель використовує серверний PHP-проксі, тому передавати токен браузеру чи налаштовувати CORS для цього прикладу не потрібно.

HTTPS обов'язковий для публічного сервера. `.htaccess` не замінює резервні копії, оновлення системи, сильні унікальні токени або обмеження запитів на рівні вебсервера/WAF.

## Перевірка перед запуском

1. Переконайся, що встановлені PHP CLI та веб-SAPI сумісної версії, `pdo_sqlite`, `json` і `curl`, а сертифікат HTTPS чинний. Запусти `php -v` і `php -m`.
2. Створи пристрій із його `id` та індивідуальним `device_token` у налаштованій SQLite-БД. Згенеруй API-токен читання для потрібного користувача в адмінці та задай його у серверному `read_config.json` панелі; для watchdog використовуй окремий токен Telegram-бота.
3. Перевір POST і GET прикладами вище. Спочатку використай тестовий ID, щоб не перезаписати стан реального пристрою. Успішний POST створює/замінює `storage/test_device.json`.
4. Перевір права користувача PHP CLI на запис у `storage/` і `states.json`, а також прямі HTTP-блокування за переліком вище.
5. Перед ручним запуском watchdog переглянь активні правила: він може негайно надіслати реальні тривоги. `php backend/watchdog.php` запускається з кореня проєкту; HTTP-запит для нього має бути заборонений.
6. Для тесту Telegram тимчасово додай правило й тестовий payload, що гарантовано його активують; після тесту віднови `rules.json` і видали тестовий файл. Успіх CLI без фактичного повідомлення не є підтвердженням доставки.
7. Після успішних ручних перевірок додай cron від імені користувача з потрібними правами. Заміни шлях і перевіряй журнал:

```cron
* * * * * /usr/bin/php /абсолютний/шлях/до/проєкту/backend/watchdog.php >> /абсолютний/шлях/до/watchdog.log 2>&1
```

`api.php` записує файл напряму через `file_put_contents`, без тимчасового файла та атомарного `rename`. При одночасному читанні й записі теоретично можливий неповний JSON; для вимог без втрати узгодженого знімка запис треба доопрацювати. Також регулярно резервуй `storage/`, `rules.json` і `states.json`.
