# Адміністративна частина Micro-IoT-Cloud

Цей каталог містить адмінку для керування користувачами, пристроями та
зв'язками доступу в SQLite. Інтерфейс працює з даними нової бази даних і не
використовує API хмарного сховища для визначення часу останнього оновлення.

## Структура файлів

- `admin.php` — сторінка керування: показує користувачів і пристрої та
  обробляє форми створення й редагування.
- `../login/index.php` — ізольована панель користувача з окремою
  автентифікацією та переглядом лише призначених йому пристроїв і JSON-стану.
- `../login/help.php` — окрема довідка користувача з локальними стилями.
- `help.php` — довідка адміністратора.
- `admin.css` і `help.css` — стилі адмінпанелі та її довідки.
- `../includes/totp.php` — спільна реалізація перевірки TOTP для обох панелей.
- `vendor/qrcode-generator.js` — локальна бібліотека для побудови QR-коду
  TOTP. QR генерується в браузері; URI та секрет не надсилаються QR-сервісу.
- `../config/config.php` — серверна конфігурація з параметром
  `database_path`; її створює `install.php`. `config.php.example` є шаблоном
  лише для локальної розробки.
- `../config/db.php` — підключає конфігурацію, створює PDO-з'єднання,
  вмикає зовнішні ключі та створює таблиці й індекс, якщо їх ще немає.
- `../config/cloud.sqlite` — стандартне місце SQLite-бази на сервері;
  інсталятор дозволяє вибрати інше ім'я файла в захищеній теці `config/`.

`admin.php` підключає `config/db.php`; шлях до каталогу бази змінюється в
`config/config.php`, а не в коді адмінки. Для першого запуску розгорни
`cloud-code/` за інструкціями в кореневому README та запусти `install.php`.
`config/db.php` створює відсутні таблиці й індекси при підключенні, тож нова
таблиця налаштувань історії додається також до наявної SQLite-бази без
видалення чи перебудови поточних таблиць.

## База даних

Ініціалізатор створює чотири таблиці:

- `users`: логін, хеш пароля, секрет TOTP, персональний `api_token`, роль і
  дата створення.
- `devices`: ідентифікатор прошивки, назва, токен запису, останній JSON-пакет
  і час його запису.
- `user_devices`: зв'язок користувачів із пристроями та рівень дозволу.
- `device_history_settings`: індивідуальні параметри ковзної історії пристрою.
  Для наявних і нових пристроїв історія вимкнена за замовчуванням.

Для `user_devices` визначено складений первинний ключ за `user_id` і
`device_id`, зовнішні ключі та індекс для пошуку за `device_id`.
Зовнішні ключі в SQLite вмикаються окремо для кожного PDO-з'єднання.

Файл SQLite, runtime-конфігурація та дані пристроїв не додаються до Git.
Серверну базу створює `install.php` у захищеній теці `config/`; локальні
файли з `sampleDB/` на сервер не завантажуються.

## Можливості адмінки

### Пристрої

- Перегляд назви, `device_id`, стану пристрою та часу останнього зв'язку.
- Стан пристрою береться з `last_payload.connected`; якщо поля немає або воно не є
  булевим значенням, показується «Невідомо».
- Стан зв'язку обчислюється за `devices.last_update`: до 15 хвилин включно —
  Online, понад 15 і до 61 хвилини включно — «Увага», понад 61 хвилину —
  Offline. Поруч показується час від останнього пакета; без коректного часу
  відображається «Немає даних». Стан оновиться після повторного завантаження
  сторінки адмінки.
- Час береться лише з `devices.last_update`. Час зміни файла через API не
  використовується. Значення з БД вважається UTC і показується в часовому
  поясі `Europe/Kyiv`, а під ним — UTC для звірки.
- Зміну назви пристрою можна зберегти; `device_id` не редагується.
- Новий пристрій створюється із заданими `device_id` і назвою. Код генерує
  випадковий токен запису; повний токен показується після створення.
- Токен можна перевипустити. Старий токен після цього перестає відповідати
  значенню в БД; новий потрібно зберегти та оновити в конфігурації пристрою.
- Можна встановити токен вручну, наприклад той, який уже записаний у прошивці.
  Введіть точне значення токена; він не показується повторно після збереження.
  Токен має містити 1–256 друкованих ASCII-символів без пробілів.
- Історію може вмикати або вимикати лише адміністратор. Доступні режими:
  вимкнено, один знімок на годину за 7 днів або один знімок кожні 30 хвилин за
  3 дні. Вимкнення видаляє файл історії пристрою.
- Параметри зберігаються як `enabled`, `interval_seconds` і
  `retention_seconds`; список режимів обмежує значення, доступні через адмінку.

### Користувачі та доступи

- Вхід дозволений лише користувачам із роллю `admin`: спочатку перевіряються
  логін і пароль, потім шестизначний TOTP-код із Google Authenticator або
  сумісного застосунку.
- Після входу сесія зберігається у стандартній PHP-сесії браузера. Вона
  завершується після 30 хвилин бездіяльності; окремого постійного
  «запам'ятати мене» немає.
- Після п'яти невдалих спроб у межах PHP-сесії вхід блокується на 5 хвилин.
- Перегляд ID, логіна, ролі й дати створення користувача.
- Створення користувача з роллю `admin` або `user`.
- Редагування логіна та ролі; порожнє поле нового пароля залишає пароль без
  змін.
- Видалення користувача з підтвердженням; його записи ACL також видаляються
  в одній транзакції.
- API-токен читання користувача можна показати повторно, згенерувати або
  перевипустити окремою дією. Перевипуск одразу робить попередній токен
  недійсним.
- `backend/read.php` приймає цей токен як GET-параметр `api_token` і повертає
  тільки пристрої, прив'язані до користувача через ACL. Для панелей токен
  слід зберігати в серверному конфігу, а не в браузері.
- Новий пароль хешується PHP-функцією `password_hash()` до запису в БД.
- Під час створення користувача генерується секрет TOTP; його QR-код і
  текстовий ключ показуються після створення.
- Кнопка скидання 2FA генерує новий секрет і показує його QR-код та ключ.
- Якщо єдиний адміністратор втратив пароль або доступ до 2FA, власник сервера
  може скористатися одноразовим recovery-скриптом із
  `../НЕ_ЗАВАНТАЖУВАТИ_НА_СЕРВЕР/reset.php`. Інструкція з розгортання та
  використання є в кореневому README. Процедура замінює пароль і 2FA разом та
  зберігає їх лише після перевірки нового TOTP-коду.
- Доступ до пристроїв користувача задається прапорцями. Для нових зв'язків
  використовується дозвіл `read`; наявний дозвіл зберігається.
- Поля `password_hash`, `totp_secret`, `device_token`, `last_payload` та
  `last_update` не редагуються вручну через форми.

### Панель користувача

- Користувач із роллю `user` входить на `login/index.php` за логіном, паролем і
  кодом TOTP. Для акаунта має бути налаштовано 2FA.
- Панель показує тільки пристрої, призначені цьому користувачу в
  `user_devices`, разом зі статусом, часом останнього зв'язку та режимом
  історії без можливості його змінити.
- JSON стану доступний лише після входу та перевірки зв'язку пристрою з
  поточним користувачем. Панель не показує API-токен і не має адмінських дій.
- Стилі панелі та довідки зберігаються в каталозі `login/` окремо від
  адмінпанелі. Обидві панелі використовують спільний TOTP-модуль із `includes/`.

### Історія пристроїв

- Увімкнена історія зберігається в `storage/<device_id>.ndjson`; кожен рядок
  містить серверний час отримання в UTC, початок UTC-слота, інтервал і JSON
  стану.
- У кожному UTC-слоті записується лише перший отриманий пакет. Порожні слоти не
  заповнюються. Прострочені записи очищуються при наступному записі або запиті
  історії; вимкнення режиму видаляє файл.
- `backend/history.php` приймає `GET` із `api_token` та `device`, перевіряє
  доступ користувача до цього пристрою й повертає NDJSON. Недоступний або
  вимкнений пристрій повертає `404`.
- Тека `storage/` заблокована від прямого HTTP-доступу; історію можна читати
  лише через endpoint із токеном користувача.

## Тестування та вимоги

Потрібні PHP 7.3 або новіший із PDO SQLite та браузер із підтримкою
JavaScript для побудови QR-коду. Під час підключення `config/db.php` файл БД
створюється SQLite, якщо він ще не існує; облікові записи та пристрої
автоматично не додаються.

Після змін перевіряйте синтаксис PHP командою:

```sh
php -l adminpanel/admin.php
php -l config/db.php
```

## Важливі обмеження безпеки

Адмінка вимагає пароль і TOTP для облікового запису з роллю `admin`,
застосовує CSRF-токени, регенерує ID сесії після автентифікації та перевіряє
роль адміністратора в БД під час кожного запиту. Обмеження невдалих спроб
зберігається лише в PHP-сесії; це не замінює серверний rate limit чи
багатокористувацький захист від перебору.

Розміщуйте адмінку лише за HTTPS: cookie сесії позначається `Secure`, коли
сервер передає PHP HTTPS-запит. Додатково обмежте доступ до адмінки на рівні
вебсервера, якщо це можливо.

Паролі зберігаються як хеші, однак `device_token`, `api_token` і `totp_secret`
наразі зберігаються в БД відкритим текстом. API-токен читається з query string, тому передавайте його
лише через HTTPS і враховуйте можливе потрапляння URL у серверні access-логи.
Новий токен показується лише після генерації, а секрет 2FA — під час
налаштування або скидання, але це не
замінює шифрування секретів у сховищі чи захисту файла БД. Зберігайте файл
SQLite поза публічно доступним каталогом вебсервера або закрийте до нього
HTTP-доступ на рівні сервера.
